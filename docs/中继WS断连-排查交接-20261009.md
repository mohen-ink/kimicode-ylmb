# 中继模式 WS 20s 断连 — 排查交接（2026-10-09）

## 现象

中继（relay）模式下，手机经 VPS 公网口打开 WebSocket（`/api/v1/ws`），
**每次都在约 20 秒被对端主动关闭**，隧道本身（worker↔VPS 注册隧道）始终
`ready` 不断——断的是「手机→桥→owner」这条 WS 子通道，不是隧道。

实测帧序列（修复前）：

```
handshake: HTTP/1.1 101 Switching Protocols
t=0.1s  data op=1 len=258      # server_hello
t=10.1s data op=1 len=103      # owner 应用层 ping
t=20.2s CLOSE frame            # 对端主动关
DONE alive=20.2s
```

## 根因（已直连 owner 实测钉死）

断连**不是中继/worker/桥的 bug**，而是 **owner 桌面端 `127.0.0.1:59879`
`/api/v1/ws` 自己的心跳协议**：

- 握手成功后 owner 下发 `{"type":"server_hello"}`；
- 每 ~10s 下发一条应用层 `{"type":"ping"}`；
- **客户端必须先回 `{"type":"client_hello"}`，再对每个 ping 回
  `{"type":"pong"}`**；任一不满足，owner 在 ~20s 以
  `close code=1001, reason="heartbeat timeout"` 主动断开。

直连 owner（绕过桥和隧道）实测：

| 行为 | 结果 |
|---|---|
| 不发 client_hello、不回 pong | `t=20.0s CLOSE 1001 heartbeat timeout` |
| 发 client_hello + 每 ping 回 pong | 存活 76s+（探针自身时长上限） |

手机面板是纯 HTTP/fetch，**从不主动开这条 WS**、也不懂 owner 心跳协议，
所以任何经 WS 进来的连接若无协议保活都会 20s 被 owner 掐掉。

## 修复（`scripts/mobile_bridge.py`，commit `1b589d2`）

桥作为「懂协议的中间人」接管心跳，对手机完全透明：

1. `_pump_bidirectional` 在双工泵启动时，**桥代手机向上游 owner 发
   `client_hello`**（掩码帧，桥对 owner 是 WS 客户端）。
2. `_ws_message_pump` 下行方向（owner→手机）拦截文本帧
   `{"type":"ping"}`：桥**直接回 `pong` 给 owner**（`source` 方向、掩码帧），
   `continue` **不透传给手机**——手机不参与心跳，也避免双 pong。

效果：owner 的心跳由桥应答，隧道 WS 不再 20s 断。

## 真机验证

`volc-mfgy` 模拟手机走完整链路
`volc → VPS(your-relay-host:47961) → 隧道 → worker → 桥 → owner`：

```
handshake: 101
t=0.1s data len=258   # server_hello
t=0.1s data len=121   # ack(我们注入的 client_hello)
...（10/20/30s 的 ping 被桥吃掉代答，不进入 data 计数）
t=90.0s DONE          # 探针 90s 上限到，WS 全程未断
```

修复前同链路 20.2s 必断 → 修复后 90s+ 稳定。

## 复测/部署注意

- 改动在 worker 进程的 `mobile_bridge` 模块内，**需重启 worker 才生效**：
  `POST /api/mobile/stop`（带 `X-Kimi-Mobile-Control: 1`）让 worker 退出，
  再 `POST /api/mobile/start {"mode":"relay"}` 拉起新 worker 即载入新代码。
- 配对 token 一次性：`POST /mobile/pair/exchange` JSON `{"token":"<pair>"}`；
  换发走 `POST /api/mobile/pair/rotate`。
- 单会话 WS 上限 `MAX_WS_PER_SESSION=4`，并发测试共用同一 SID 即可。
- 上线前仍建议实体手机扫码走一遍配对+用量页+长挂（>5min）确认无回归。

## 追加：第二层「一连就断」根治（commit 95f2b90）

### 现象
配对/WS 心跳修好后，仍出现「手机一连接 ~160s 就整线掉」，VPS `relay_server.log`
显示隧道活不过几分钟即 unregistered。

### 根因（两层叠加）
1. **relay 掉线无重连**：`RelayClient._run` 原来断线即 `_fail('TUNNEL_EXITED')`
   → `_stop_generation` 全量 teardown（关 sockets、清 `_sessions`/`_pair_tokens`、
   停 relay/connector）。任何一次网络抖动都 = 全断。
2. **请求热路径误杀**：`_owner_still_mine`（内含 2.5s healthz `_owner_responds`）
   被 `upstream_snapshot` / `first_authorization_valid` / `rotate_pair` 在每个
   HTTP/WS 请求上调用；单次 healthz 抖动 → 直接 `_stop_generation('OWNER_LOST')`
   拆隧道。手机一连 → 触发请求 → 一抖就全断。standalone `RelayClient` 不经过
   owner 检查所以稳——这就是「脚本稳、面板掉」的反差来源。

### 修复
- `mobile_relay.py::_run`：断线改指数退避自动重连（`RECONNECT_BASE=1s`→`RECONNECT_MAX=30s`，
  累计 `RECONNECT_GIVEUP=300s` 仍连不上才 `_fail('TUNNEL_EXITED')`）；`_connected_once`
  标记本轮是否曾 `_ready`，连上后复位退避；`stop()/shutdown()` 仍即时退出。
- `mobile_bridge.py` 三处热路径（`upstream_snapshot`/`first_authorization_valid`/
  `rotate_pair`）：owner 疑似失联只让本请求失败（503/False/raise），**不就地 teardown**；
  teardown 统一由 `_watch_owner` 连续 `OWNER_LOST_GRACE=3` 次确认后执行。

### 实测
- relay 隧道 **203s 连续 on/ready 零掉线**（此前 160s 必 TUNNEL_EXITED）。
- 配对 exchange 200 发 cookie → `/mobile/usage` 200、`/mobile/usage/data` 200、
  `/api/v1/models` 200（经 relay 转发 owner）。
- WS 经 relay `101` 握手 → 收 `server_hello`+`ack` → 65s 不断。

### 排查陷阱记录
- 配对 token **每次 rotate 全部作废重签**；用旧 token 测 exchange 必 403
  「配对码无效或已过期」——这是校验正常结果，不是断连。
- 本机桥直连 127.0.0.1:<port> 会被 Host 白名单拒（`Host 不被允许`）——relay
  模式只认 `_public_origin`（`your-relay-host:47961`）的 Host，必须经 VPS 公网口测。
- POST `/mobile/pair/exchange` 必须带 `Origin: http://<vps>:<port>`，否则 Origin
  校验 403。
