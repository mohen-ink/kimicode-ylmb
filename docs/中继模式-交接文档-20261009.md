# 中继（relay）手机远程模式 — 交接文档

> 面向接手继续修的人。日期 2026-10-09。分支 `feat/mode-slider`（本机，未推送仓库）。
> 所有密码/共享密钥均不写明文；VPS 共享密钥在代码常量里本就是私人测试值，可直接看源码。

## 一、这套东西是什么

用量面板插件新增「手机远程访问」能力：手机浏览器打开一个公网 URL，就能看/操作本机
Kimi Code 桌面端的会话与用量。三种接入模式：

| 模式 | 链路 | 状态 |
|---|---|---|
| LAN | 手机直连本机局域网 IP | 内网才通，出不了门 |
| internet | cloudflared trycloudflare 隧道 | 卡、不稳，海外 |
| **relay（本次重点）** | 自建 VPS 中继 | 已能跑通，仍有问题要收尾 |

relay 拓扑：

```
手机浏览器 ──HTTP/WS──> VPS 公网口 :47961 (/t/<tid>/...)
                            │  同一条隧道 WS 复用
worker(本机插件进程) ──WS──> VPS 注册口 :48213 (/relay/register, X-Relay-Token)
                            │
                            └─> 本机桥 HTTP(127.0.0.1:39282) ──> owner 桌面端 :49655
```

- **VPS 侧**：`scripts/relay_server.py`（asyncio 单文件，纯标准库）。注册口收 worker，
  公网口按 `/t/<tunnel_id>/rest` 路由到对应隧道。
- **worker 侧**：`scripts/mobile_relay.py`（`RelayClient`，跑在本机插件 worker 进程里），
  把隧道来的 HTTP/WS 转成对本机桥的请求，回传响应。
- **本机桥**：`scripts/mobile_bridge.py`（`_LanHTTPServer`/`_LanHandler`），安全边界：
  Host/Origin 白名单、配对 token、会话 cookie、WS 上限、owner 存活判定都在这层。
- **前端**：`assets/kimi-usage-widget.js`（含模式滑块/档位编辑器 kmd* 一族函数）。

## 二、配置文件

- worker 读 `~/.kimi-code/usage-dashboard/relay.json`：
  `{"host":"114.66.24.119","tunnel_port":48213,"public_port":47961,"token":""}`
  （token 由本机 `relay.json` 或 `KIMI_RELAY_TOKEN` 环境变量提供，仓库不再内置默认值）
- owner 桌面端实例登记：`~/.kimi-code/server/instances/<server_id>.json`
  （`pid`/`port`/`server_id`，worker 靠它定位+验活 owner）

## 三、控制面（本机调试入口）

daemon 在 `127.0.0.1:39281`，全部要头 `X-Kimi-Mobile-Control: 1` + `Host: 127.0.0.1:39281`：

```
GET  /api/mobile/status                 # 状态：state/tunnel/pair_state/url
POST /api/mobile/stop                   # 停 worker
POST /api/mobile/start                  # 起 worker；body {"mode":"relay","owner_origin":"http://127.0.0.1:49655"}
POST /api/mobile/pair/rotate            # 换新配对 token（旧的全作废）
```

## 四、已经修好的坑（按时间序，含根因）

### 坑1：WS 20s 必断 — owner 应用层心跳
owner `/api/v1/ws` 要求握手后客户端先回 `client_hello`、之后每 ~10s 回应用层
`ping/pong`，否则 ~20s 以 `1001 heartbeat timeout` 断开。手机端不知道这套协议。
**修法**（commit `1b589d2`，`mobile_bridge.py`）：桥在 `_pump_bidirectional` 启动时
代发 `client_hello`；`_ws_message_pump` 下行拦截 `{"type":"ping"}` 代答 `pong`，不透传手机。

### 坑2：「一连就断」~160s 整线掉 — 两层叠加（commit `95f2b90`）
1. **relay 断线无重连**：`_run` 原来断线即 `_fail('TUNNEL_EXITED')` → `_stop_generation`
   全量 teardown（关 sockets、清会话/配对 token、停 relay）。→ 改为指数退避自动重连
   （`RECONNECT_BASE=1s`→`RECONNECT_MAX=30s`，累计 `RECONNECT_GIVEUP=300s` 才认败）。
2. **请求热路径误杀**：`_owner_still_mine`（含 2.5s healthz）被 `upstream_snapshot`/
   `first_authorization_valid`/`rotate_pair` 在每个请求上调用；单次抖动就 teardown。
   → 这三处改为「疑似失联只让本请求失败」，teardown 统一交 `_watch_owner` 连续
   `OWNER_LOST_GRACE=3` 次确认。**这是「脚本稳、面板掉」的反差根因。**

### 坑3：「tunnel not found」— 重连 tid 变了（commit `f17d876`）
VPS 原每次注册发随机 `tid`；worker 重连拿新 tid，但手机配对 URL 里是旧 tid → 路由 404。
**修法**：tid 粘滞。
- `relay_server.py`：新增 `RECENT_TIDS` 墓碑表（注销记入，`RECENT_TTL=600s` 上限512）；
  注册时读 `X-Relay-Resume` 头，tid 仍活或墓碑未过期则复用而非随机。
- `mobile_relay.py::_run_once`：握手带 `X-Relay-Resume: <上次 tunnel_id>`。
- `mobile_bridge.py::_tunnel_ready`：放宽到 `state=='on'`（重连二次 ready）仅刷新
  origin/tid，首次 `starting→on` 才发配对 token。

**注意：VPS 上的 `relay_server.py` 必须更新到本版**，否则 `X-Relay-Resume` 被忽略、
tid 仍旧随机。当前 `114.66.24.119:/root/relay_server.py` 已部署新版并验证（强杀连接
后 6s 重连复用同一 tid）。

### 坑4：滑块编辑器保存后不刷新（commit `95f2b90`，前端）
`/api/modes/save` 只更新档位定义不改 config.toml，`active` 由 `detect_active_mode`
按当前 config 反推。原代码保存后延迟 350ms 才 render 且 range 聚焦时跳过 value 更新。
**修法**（`kimi-usage-widget.js`）：保存成功立即 blur+清拖拽态+`kmdRender`+`kmdSnapTo`
吸附到 `active`；`active==null`（编辑改到不匹配）时滑块回 `last_applied.index` 兜底，
ticks 高亮/名称栏跟随滑块实际位置。

## 五、实测结论（本机，2026-10-09）

- relay 隧道 **203s 连续 on/ready 零掉线**（修复前 ~160s 必 TUNNEL_EXITED）。
- 配对 `POST /t/<tid>/mobile/pair/exchange` 200 发 `kimi_mb` cookie →
  `/mobile/usage` 200、`/mobile/usage/data` 200、`/api/v1/models` 200。
- WS 经 relay `101` → 收 `server_hello`+`ack` → 65s 不断。
- 强杀 VPS 隧道连接 → 6s 后 worker 自动重连且**复用同一 tid**。

## 六、仍需接手收尾 / 注意

1. **配对 token 一次性**：每次 `pair/rotate` 旧 token 全作废；用旧 token 测
   `exchange` 必 403「配对码无效或已过期」——是校验正常，不是 bug。
2. **本机桥直连会被 Host 白名单拒**：`127.0.0.1:39282` 直接打返回「Host 不被允许」，
   relay 模式只认 `_public_origin`（`114.66.24.119:47961`）的 Host。**测公网链路必须
   经 VPS 公网口**，别直连桥。
3. **exchange 必须带 `Origin: http://<vps>:<port>`**（POST 触发 Origin 校验），否则 403。
4. **墓碑表是内存态**：`relay_server.py` 重启后 `RECENT_TIDS`/`TUNNELS` 清空，所有 tid
   失效，worker 需重连（会自动）但手机端要重新配对。若要重启不丢 tid，得把 tid 落盘或
   用确定性 tid（如按 worker 标识 hash）——**未实现，是下一步候选**。
5. **relay 全程明文 http**（无 TLS），公网暴露裸奔，token 仅注册握手用，传输内容可被
   中间人看。公开给用户前建议套 TLS 或至少换强 token + 限源 IP。
6. **relay.json 里 token 为空走默认密钥**——面板「保存」时若没填 token 会回退到代码里
   的私人测试密钥。公开版要么强制要求填、要么把默认值清空。
7. 单会话 WS 上限 `MAX_WS_PER_SESSION=4`；`_exchange_fails` 有失败计数封禁
   （`EXCHANGE_MAX_FAILS`/`EXCHANGE_BAN_SECONDS`），多机压测同一来源 IP 可能被误伤。

## 七、快速自检命令

```bash
# 状态
curl -s http://127.0.0.1:39281/api/mobile/status -H "X-Kimi-Mobile-Control: 1" -H "Host: 127.0.0.1:39281"
# 重启 worker 加载新代码
curl -s -X POST http://127.0.0.1:39281/api/mobile/stop  -H "X-Kimi-Mobile-Control: 1" -H "Host: 127.0.0.1:39281" -d "{}"
curl -s -X POST http://127.0.0.1:39281/api/mobile/start -H "X-Kimi-Mobile-Control: 1" -H "Host: 127.0.0.1:39281" -d '{"mode":"relay","owner_origin":"http://127.0.0.1:49655"}'
# VPS 侧看注册
ssh root@114.66.24.119 'tail -30 /root/relay_server.log'
```
