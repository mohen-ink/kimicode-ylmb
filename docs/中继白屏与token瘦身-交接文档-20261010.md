## 二、坑1：中继白屏（核心，最花时间）

### 现象

- 本地模式（局域网 / 直连 owner）页面**正常**；
- 走自建中继**白屏**，只渲染出右下角「用量」按钮；
- 服务器日志里隧道**反复** `unregistered` / `registered`（秒级抖动）。

### 排查路径（含走过的弯路，避免重复）

先用**同源对照**排除法定位：

| 实验 | 结果 | 结论 |
|---|---|---|
| 非安全上下文 `http://<内网IP>:port/` 直连 owner | 完整渲染 | 排除「HTTP 非安全上下文」 |
| 非安全上下文经**局域网桥**（同样改写 HTML） | 完整渲染 | 排除「桥改写 HTML」「`crypto.randomUUID`」 |
| 经**真实 VPS 中继** | **白屏** | 问题锁定在「经隧道」这一段 |

> 弯路记录：一度怀疑 `crypto.randomUUID`（安全上下文才提供）与 SPA 路由前缀，
> 均被上述对照实验证伪。**不要**再从这两个方向查。

再看服务器逐请求日志，规律很清楚：

```
14:32:43,731 GET /assets/main-CWg721rQ.js -> 200 3538558B 1.49s
14:32:43,733 tunnel unregistered: a0-8toC8q6g      ← 差 1 毫秒
14:32:44,587 tunnel registered: a0-8toC8q6g
```

`main.js`（3.5MB，SPA 入口）**传完的同一毫秒隧道就掉**，而独立 `<script>` 引入的
「用量」按钮不受影响 —— 正好解释「白屏 + 只剩用量」。

### 根因（探针实测钉死）

给 worker 的 socket 加发送探针，抓到：

```
SENDALL_FAILED len=211671 err=TimeoutError('timed out')
```

`mobile_relay.py` 里隧道 socket 设了 `RECV_POLL = 0.5` 秒超时。**Python 的 socket 超时
读和写共用**，于是 `sendall` 也继承了这 0.5 秒：

1. 任何**发不完 0.5 秒**的帧（211KB 就超，3.5MB 的 `main.js` 必超）抛 `socket.timeout`；
2. `send_frame` 捕获后把 `self.alive = False`，**整条隧道判死**；
3. 服务器立即 `unregistered`，worker 1 秒后重连。

本地/局域网不经隧道，转发是本机内存操作，永远不会触发，所以「本地能开、中继白屏」。

### 修复（`scripts/mobile_relay.py`）

1. **发送超时与读轮询分离**：新增 `SEND_TIMEOUT = 60.0`；`send_frame` 发送前临时调大、
   发完在 `finally` 里复位为 `RECV_POLL`；读路径每次 `recv` 前复位为 `RECV_POLL`，
   保证读不会长时间阻塞、`stop()` 能及时生效。
2. **掩码提速**：新增 `_mask_payload()`，用大整数一次异或替换逐字节生成器
   （4MB 掩码从**数秒**降到 **0.01 秒**），与服务器端 `_xor_mask` 保持一致。
   掩码是发大帧前的必经步骤，慢在这里同样会顶到发送超时。

## 三、坑2：WS 子协议导致「实时连接出错」

中继的 101 响应不回显浏览器请求的 `Sec-WebSocket-Protocol`，而 SPA 用
`kimi-code.bearer.<凭据>` 子协议承载登录态；浏览器规定服务端**必须回显**所选子协议，
否则直接判握手失败。桥自己会回显，中继不会 —— 修它**必须同时改服务器**。

修复（`scripts/relay_server.py`）：101 响应里回显第一个 `kimi-code.bearer.*`
子协议（桥对该子协议只校验 `kimi-code.bearer.` 前缀，故原样回显即可）；没有则不发该头。

> 注意：这与 `docs/中继WS断连-排查交接-20261009.md` 是**两个不同问题**。
> 那篇讲 owner 应用层心跳 20s 断连（桥代回 `client_hello` + `pong`），已修复。

## 四、同批带入的服务器版同步（须知情）

当前工作区的 `relay_server.py` 相对 v3.4.0 原版（643 行）是**联调验证版（729 行）**，
除上面的 WS 回显外，还包含这些**已在生产运行**的改动：

- `TUNNEL_MAX_FRAME = 192MiB`：旧版误用 `MAX_WS_MESSAGE`(4MB)，SPA 主包 3.5MB →
  隧道帧 4.7MB 超限 → 隧道被判违例拆掉。
- 根路径隧道归属：`RELAY_COOKIE = 'kimi_relay_tid'` + `_root_tid()`（Cookie → Referer），
  让 `/assets/*`、`/api/v1/*` 这些**不带 `/t/<id>/` 前缀**的根绝对路径能正确归位；
  多隧道且无归属时 404（fail-closed，绝不猜）。
- `_await_tunnel()` + `RECONNECT_WAIT`：重连空档期内请求最多等 10 秒，返回 503 而非 404。
- 注销竞态修复：`if TUNNELS.get(tid) is tun` 才 pop，避免重连时误删新隧道。
- `_xor_mask()` 大整数异或；逐请求日志（`GET /assets/... -> 200 ...B ...s`）。

> **踩过的坑**：部署时曾用新版直接覆盖服务器文件，把队友新加的**逐请求日志**覆盖没了。
> 已从备份取回并补进仓库，现生产版本与仓库**逐字节一致**。以后部署前先 diff 服务器现状。

## 五、坑3：共享 token 从代码与历史移除

### 现状

- 服务器 `relay_server.py` 是**单 token 校验**（`--token` 只认一个值）。
- 仓库原在 `mobile_relay.py` 硬编码 `DEFAULT_RELAY_TOKEN`，**且已在提交 `503f062` 里**
  （不只是工作区）。该分支从未推送，远端干净，但一旦推送即泄露。
- **澄清一个我曾经说错的点**：单 token 共享**不会**让多客户端互相顶隧道。
  token 只在注册时做准入检查（`compare_digest`），之后退场；隧道身份是每个客户端
  各自随机的 `tid`，互不影响。「隧道反复断」是坑1的发送超时 bug；「一直正在开启」
  是 token **填错**（403）。**不是** token 共用造成的。

### 措施

1. **代码**：`DEFAULT_RELAY_TOKEN = ''`（不再内置任何 token）；token 只从
   `~/.kimi-code/usage-dashboard/relay.json` 的 `token` 字段或 `KIMI_RELAY_TOKEN`
   环境变量读取。空串 = 不发 `X-Relay-Token`（仅服务器未启用 `--token` 时可用）。
2. **文档同步**（否则成假描述）：`CHANGELOG.md` 与三份手机文档里「源码内置默认 token」
   的表述，全部改为「token 不内置仓库，只存于部署环境与本机 `relay.json`」。
3. **历史重写**：分支从未推送，故把「去 token」并入原合并提交 `503f062`（重写为
   `ac86f59`），中继修复单独成 `0e1dbd4`。**全历史遍历确认 token 零命中。**

### 关键决策（用户明确要求）

- **保持单 token 共享**，不做多 token（不做"每人一把、可单独吊销"）。
- **token 值本身不改**，只是不再进仓库。所以**旧 token 仍然有效**。
- 用户判断「目前还没泄露」。

## 七、仍需接手收尾 / 注意

1. **新装用户必须填 token**：仓库不再兜底。若通过更新器拿到新版 `mobile_relay.py`
   而 `relay.json` 无 token，会连不上 —— 需在界面「中继服务器配置」填一次。
   **不要**在密钥框里随手填（填错就是「一直正在开启」，服务器 403）。
   想只改端口/地址时，**密钥框留空**即保持原值。
2. **配置三处必须一致**（否则一边对一边错）：
   - 服务器 `--public-port`（默认 47961，`--public-host` 决定注册回执里的 origin）
   - 服务器 `--token`
   - 本机 `relay.json` 的 `host` / `tunnel_port` / `public_port` / `token`
3. **服务器重启会全员掉线**（单进程无守护）；`/root/start_relay.sh` 里硬编码了
   `--token`，改 token 需同时改它。
4. **旧 token 仍有效**，且曾出现在某次对话中。若判断有风险，换一把需同步
   服务器 `start_relay.sh` + 运行进程 + 各客户端 `relay.json` 三处。
5. **手机远程连接整体仍是预览功能**：真实蜂窝网真机扫码、长时稳定性**尚未验收**。
   本合同不声明公网验收已通过。
6. **自建中继是明文传输**（`ws://` / `http://`）：配对码、Cookie、会话与文件内容经
   VPS 时不保密。仅限自控服务器、临时联调场景。

## 八、快速自检命令

```bash
# 本机：中继能否连上（token 从 relay.json 取）
cd <插件目录>/scripts
python -c "import relay_config,os;c=relay_config.load(os.path.expanduser('~/.kimi-code'));print(c['host'],c['public_port'],'token_set=',bool(c['token']))"

# VPS：进程与端口
ssh root@<vps> "ps aux|grep relay_server.py|grep -v grep; ss -ltnp|grep -E '48213|47961'"

# VPS：隧道注册/注销（有抖动即异常，正常应一次注册长期不注销）
ssh root@<vps> "grep -c 'tunnel registered:' /root/relay_server.log"

# 令牌校验是否匹配（403=token 不对，101=通过）
#   注意：--token 不传则服务器不校验
```
