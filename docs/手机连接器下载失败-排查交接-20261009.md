# 手机连接器「下载不了」排查与交接（2026-10-09）

适用版本：v3.3.3 ~ v3.3.5 出问题，v3.3.6 修复。执行人：Mina-kk。

## 1. 现象

侧栏「手机」→ 同意安装 Cloudflare 连接器后，几秒内失败，提示「组件完整性校验失败」（错误码 `CONNECTOR_HASH_MISMATCH`）。重试结果相同。看上去像「下载不了」或「下载被篡改」。

## 2. 结论

**不是网络问题，也不是哈希问题**，是路径安全检查误伤了目录联接（junction），然后错误码又报错了。

1. 出问题的电脑上，`C:\Users\<用户>\.kimi-code` 是一个目录联接（junction），指向别的盘，比如 `D:\Mina\kimi-code-home`。把 Kimi 主目录搬到其他盘的用户常这么做。
2. `scripts/mobile_tunnel.py` 的 `_read_packaged_license()` 会逐级检查随包许可证 `assets/vendor/cloudflared-2026.9.3-LICENSE` 的每一层父目录，带 reparse 属性（0x400）的一律拒绝。这个路径用 `Path(__file__).absolute()` 构造，不解析联接，所以 `.kimi-code` 这一层被拒，抛出 `OSError('packaged license directory rejected')`。
3. `_install_worker()` 里错误码初值是 `CONNECTOR_HASH_MISMATCH`，读许可证这一步就失败了，于是界面显示「完整性校验失败」。这时连接器其实还没开始下载。
4. 第二处同类问题：`ConnectorRuntime._check_directories()` 会检查 `self._home`（即 `~/.kimi-code`），修好第 2 点后会变成 `runtime directory rejected`，表现为 `CONNECTOR_INSTALL_FAILED`。
5. `mobile_worker._ensure_runtime_dir` 只检查 `runtime/mobile-worker` 这些子目录，不受影响，所以 worker 能正常拉起，只有连接器安装失败。

## 3. 复现与证据（本机）

- `~/.kimi-code` 为 JUNCTION → `D:\Mina\kimi-code-home`；解析后的路径 `D:\Mina\kimi-code-home`、`D:\Mina`、`D:\` 都不是 reparse point。
- 用探针脚本直接 import 安装目录里的 `mobile_tunnel`：
  - 修复前：`_read_packaged_license()` 抛 `packaged license directory rejected`。
  - `_download(CONNECTOR_URL)` 本身正常：3 秒下完 55366080 字节，SHA-256 与 `CONNECTOR_SHA256` 一致。
  - 随包 LICENSE 大小 11357，SHA-256 `58d1e17f…`，正确。
- 网络：直连 github.com 正常；raw.githubusercontent.com 被重置，但安装流程用随包许可证，不访问它；api.trycloudflare.com 与 `region1.v2.argotunnel.com:7844` 可达。

## 4. 修复（v3.3.6，`scripts/mobile_tunnel.py`）

| 位置 | 改动 |
|---|---|
| `_PACKAGED_LICENSE` | `Path(__file__).absolute()` → `Path(os.path.realpath(__file__))` |
| `ConnectorRuntime.__init__` | `self._home` 先 `os.path.realpath` 再用 |
| `_install_worker` | 错误码初值改为 `CONNECTOR_INSTALL_FAILED`；只有许可证摘要/大小真的不符（`ValueError`）才报 `CONNECTOR_HASH_MISMATCH` |
| User-Agent | `kimi-mobile-connector/3.3.2-local` → `kimi-mobile-connector/3.3.6` |

安全约束不变：先解析成真实路径，再对真实路径逐级做「不是符号链接、不是 reparse point」检查。联接本身只作为入口，不会把运行时文件写到可被替换的链接后面。

`scripts/mobile_worker.py` 的 `WORKER_VERSION` 从 `3.3.3` 升到 `3.3.6`。原因：同版本的 worker 会被新后台直接接管，旧进程里还是旧的 `mobile_tunnel` 代码，修复不会生效。升版本后会走已有的「旧版本助手 → 提示先停止」路径。

## 7. 发版与更新链路

- 推 `v*` tag 会触发 `.github/workflows/release.yml`：校验 tag 和 `kimi.plugin.json` 版本一致，`git archive` 打 `kimicode-ylmb-<版本>.zip` 与 `.sha256`，发 Release（正文取 CHANGELOG 对应节）。
- Release 资产命名历史上不统一：v3.2.x 是 `kimi-code-usage-vX.zip`，v3.3.3 是 `kimicode-ylmb-v3.3.3.zip`，CI 是 `kimicode-ylmb-3.3.6.zip`（不带 v）。今后以 CI 为准。
- 面板内更新器下载的是 `codeload.github.com/.../zip/refs/heads/main`，**不依赖 Release 资产**；只要 main 上的 `kimi.plugin.json` 版本号更高就会提示更新。
- 升级到 3.3.6 时，如果手机连接正在运行，先点「停止」，再开启。

## 8. 用户侧临时方案（未升级时）

- 用 v3.3.5+ 的**内网模式**：手机和电脑在同一局域网时可用，不需要 cloudflared。
- 或者把 Kimi 主目录改回真实目录，不用 junction（不推荐，改动大）。

## 9. 安全提示

- 配对链接 / 二维码 = 控制本机 Kimi 的授权，10 分钟内一次性有效，不要发到群里或截图外传。
- 内网模式是明文 HTTP，只在可信局域网使用。
- 用完点「停止」：会撤销隧道、配对和全部会话。
